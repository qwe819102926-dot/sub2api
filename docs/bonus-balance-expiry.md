# 赠送余额有效期

- 每笔赠送从到账时起有效一个自然月，按北京时间计算；月末在下个月没有对应日期时，取下个月最后一天的相同时刻。
- 到期时刻起不可使用。优先扣减最早到期的额度，后续赠送不会延长旧额度的有效期。
- 注册、邀请、签到、充值赠送、消费奖励、抽奖和管理员赠送均适用。
- 充值本金、消费倍率和账单金额的计算规则不变。过期流水来源为 `expiration`，计入历史账本“其他扣减”，不计为消费。

## 历史余额迁移

迁移 `254_bonus_balance_expiry.sql` 在同一个事务中锁定钱包、建立逐笔额度和清理已过期余额。迁移前应保留数据库备份，并安排维护窗口；本地测试不代表已执行线上迁移。

剩余额度根据现有钱包余额，从最近的正向入账向前分配，等价于历史消费优先使用旧额度。历史统一除以十的换算会转换到现有余额单位，并保留原到账日期。此过程保留原始流水，不会再次发奖。

能还原到账日期的剩余额度按原日期计算到期时间，满一个月的在迁移时立即失效。对于 `historical_credit` 来源不明补录或无法匹配到账记录的余额，按用户选择给予迁移生效起一个自然月的宽限期，并通过 `date_estimated` 标记。历史消费只有按日汇总时，逐笔归属以此 FIFO 恢复规则为准。

## 一致性与清理

`bonus_balance_lots` 保存每笔的剩余额度与到期时刻；数据库触发器覆盖所有现有赠送入口。消费、管理员改余额和过期清理都锁定同一用户行，相关余额、额度与流水在同一个事务中提交或回滚。余额单位转换按累计值舍入到八位小数，保持额度合计与钱包完全一致。

鉴权、消费预检、用户余额接口和管理端用户明细只读有效额度。实际扣费在同一事务内先清理到期额度，再按倍率扣减有效赠送，最后扣本金。因此即使后台清理任务延迟，过期赠送也不能继续用于消费。

已有后台到期服务每分钟清理最多 500 个账户，每个账户单独提交；多实例共享领导锁，单用户行锁确保重复清理不会重复扣款。历史账本汇总使用已落账金额，可能在后台清理前短暂包含待清理余额。

## 本地验证

使用独立、可丢弃的本地 PostgreSQL 数据库，配置 lib/pq keyword 格式的 `SUB2API_CONVERSION_TEST_DSN` 后运行：

```text
go test ./internal/service -run TestBonusExpiryPostgres -count=1
go test -tags unit ./internal/repository -run 'TestBonusExpiryRepository|TestGetBonusBalanceCredit|TestDeductUsageBillingBalance' -count=1
```

覆盖旧余额即时过期、历史单位换算、日期不明宽限期、月末和闰年、FIFO、新奖励不续期、精度、并发重复清理、回滚、过期额度鉴权不可用、混合余额与倍率、管理员改余额。
