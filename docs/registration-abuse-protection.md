# 邮箱注册防滥用

本次更新针对“浏览器形式注册，再由程序修改资料”的已观察流程。User-Agent 可伪造，不能凭 `node`、英文用户名或注册间隔判定恶意，也不能保证阻止能持续完成真实人机验证的浏览器自动化。

## 更新后的流程

1. 发邮箱验证码：检查浏览器 UA，验证当前启用的人机验证服务，检查 Redis 共享限额，然后发送邮件。
2. 邮件入队成功后，设置 10 分钟有效的随机注册凭证 Cookie。它为 HttpOnly、SameSite=Strict，在 HTTPS 下为 Secure，路径限定为 `/api/v1/auth`；不向前端 JS 返回票据。
3. 最终注册：核对 Cookie、邮箱和 UA 的绑定，并独立校验新的验证码服务票据。邮箱验证码不再跳过最终的人机验证。发邮件时用过的票据不能继续使用。
4. 同一个凭证只允许一个请求同时处理。输错邮箱验证码后可以重试，但需重新完成人机验证；注册成功后消费凭证并清除 Cookie。
5. 注册成功审计绑定新用户 ID，便于关联注册时的 IP、UA、请求 ID 与后续行为。

凭证不绑定 IP，以允许正常用户在 Wi-Fi 和移动网络之间切换。Redis 不可用时拒绝发码、注册，不退回无校验模式。

## 默认限额

以下窗口从首次请求开始计时；计数与过期在 Redis Lua 中原子处理，跨应用实例共享。

| 维度 | 限额 |
|---|---|
| 同 IP | 10 分钟 3 次发码、24 小时 10 次 |
| 同邮箱（忽略大小写、首尾空格） | 24 小时 5 次发码 |
| 同 IPv4 /24 或 IPv6 /48 | 24 小时 50 次发码 |

IPv6 在同一个 /64 内轮换地址仍算同一个 IP。邮箱验证关闭时，上述限额用于直接注册尝试。现有每分钟接口限流仍保留。

限额是发码/注册尝试数，不是成功账号数。验证码服务校验失败不会消耗上述发码额度；邮件入队失败可能消耗一次额度。共享网络和频繁重发可能触发限额，页面会提示稍后再试或联系客服。阈值集中于 `backend/internal/service/registration_guard.go`。

## 部署和兼容性

- 后端和前端需同时发布。发布前已经发送邮件但没有新 Cookie 的流程，需要重新发码。
- 普通注册只支持网站浏览器流程。原来直接调用注册接口的客户端需要调整；已有用户登录和模型调用不受此注册规则限制。
- 浏览器和 API 应在同一站点使用。跨站点分离部署不适用当前 Strict Cookie 策略。
- 保留站点原有人机验证服务选择；当前生产启用 Turnstile。若管理员关闭人机验证，凭证与额度仍生效，但真人检测能力随之降低。
- 限流 IP 复用应用现有的 `SessionBindingContext` / `SecurityClientIP` 解析策略，不能把 Caddy 地址当成全部用户地址。部署时应检查可信代理配置：明确列出实际代理地址，并在代理链验证通过后关闭旧版原始转发头信任。否则旧兼容模式允许信任原始转发头，IP 计数不能作为可靠的单独防线。此次未修改线上代理或 IP 解析设置。
- 不修改账号、赠金、签到或邀请返利规则，不需要数据库迁移。已有可疑账号的处置需单独决定。

## 验收

- 正常网页：发码、在同一浏览器输入邮箱验证码、完成人机验证、注册成功。
- 直接 `node` 请求：发码和注册均被拒绝。
- 伪装浏览器但缺少注册 Cookie、换邮箱或 UA、重放过期/已消费的 Cookie：被拒绝。
- 有有效注册 Cookie 和邮箱验证码，但缺少新的验证码服务票据：被拒绝。
- 输错邮箱验证码后，在原浏览器重新完成人机验证可重试；并发请求不能重复消费凭证。
- 同 IP、邮箱、网段超限：被拒绝；时间窗口到期后恢复。

这会使目前没有最终人机验证票据的旧注册调用失败；若对方适配新流程并通过每次人机验证，仍需根据运行证据进一步收紧或改为邀请/审核注册。
